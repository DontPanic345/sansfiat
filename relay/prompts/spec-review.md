# Spec-review step

You're the one who runs things. The designer planned by reading; you check the plan against
the code and the maps. Read the code each settled rule touches. Where minutes of running
would settle a number or drop a fallback, run the sweep or a play script. Where the run
disagrees with the reading, the run wins: fix the plan.

Then look for what the designer didn't consider:

- a design line it reads differently
- a case it doesn't cover
- a number that can't pass on the real maps
- a proof that runs only on a built map
- a brief that fixes what its build should find by measuring
- a step not worth its own session
- a shape that doesn't fit the piece, or a score that doesn't fit its part

Fix them in the spec, the briefs and `steps.json`: the crew makes the steps from what you
leave. Leave to the builds what the checks tell them in seconds. You're done when
`steps.json` reads as the spec step's rules say.
